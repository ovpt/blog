# 早期发现漏洞的方向

并列文档：[进阶指南](进阶指南.md)。实验编号 L0–L19 都在那份指南里，通过标准也在那里。本文只回答：在这台 iPhone XS Max、iOS 18.7 上，先做哪一块，才比较早得到一次可以写进笔记的结果。

核对日期：2026-10-31（北京时间）。当时这台手机的最新正式版是 iOS 18.7.11。你手头的 18.7.9 发布于 2026-05-11，安全说明在 <https://support.apple.com/en-us/127111>。

## 结论

先做 WebKit 里能用一句话写清的逻辑不变量：内容安全策略（CSP）、同源策略、script message handler 的来源、导航相关的来源检查。

原因有三条，都绑在这台机器上。

1. iOS 18.7.9 的安全说明里，WebKit 占了多条，而且集中在 CSP 被绕过、CSP 没在 AudioWorklet 里执行、处理网页导致信息泄露、处理网页导致进程崩溃。同一支系统更早的 18.7.7 说明里还有同源策略和 script message handler 跨来源。索引在 <https://support.apple.com/en-us/100100>。
2. WebKit 源码公开，可以在 Mac 上读到修复和回归测试。回归测试就是在断言「这个来源不能读那个来源」或「这条 CSP 必须挡住这段脚本」。你在 L15 已经见过这种句子。
3. 这台 A12 跑 iOS 18.7，没有本指南会使用的越狱研究环境。内核、Wi-Fi 芯片、被利用过的闭源图形解析器，在这台手机上给不了带符号的崩溃栈。先做它们，几天之内没有可复现的笔记，信心会掉在工具上，而不是掉在判断上。

第一份「不是玩具」的笔记，预期出现在 L16：你能指着一个调用点说，修复加的检查这里没有，并把它标成「候选」。它还不是漏洞。漏洞是 L15 那种运行中的系统说出了 `UNEXPECTED`，或你在自己编的二进制里拿到 ASan 报告，并且能指出攻击者控制的是哪一个字段。

## 不要从这些模块开始

下面这些都在你这台手机的近期公告里出现过。把它们放后面，是因为现在证实不了，不是因为不重要。

| 模块 | 18.7.9 或 18.7.11 公告里的类型 | 现在拿它当起点的结果 |
| --- | --- | --- |
| WebKit 的 CSP、同源、消息桥 | 逻辑问题、信息泄露、崩溃。18.7.9 有多条 | 可以读、可以在 Mac 上对照。这是起点 |
| zlib | 18.7.9：访问恶意网页可能泄露数据 | 源码能编。L14 把流水线跑通。30 秒 fuzz 通常没有新崩溃，这是正常的 |
| App Intents | 18.7.9：恶意 App 可能逃出沙盒，逻辑问题 | 公开源码编不出这个组件，无法对照「修复前 / 修复后」 |
| 内核、IOKit、APFS、IOHIDFamily | 18.7.9：多条内存破坏、信息泄露，其中一条是 App 获得 root | 未越狱的手机上看不到带符号的内核栈 |
| Wi-Fi | 18.7.9：有一条是 App 以内核权限执行代码 | 同上，而且复现会碰到无线输入。不作为起步 |
| ImageIO、Model I/O、Quick Look、SceneKit | 18.7.9：处理文件导致崩溃或信息泄露 | 设备上的实现是闭源的 |
| CoreGraphics | 18.7.11：处理恶意文件可能导致任意代码执行。Apple 写明，有报告称该问题曾在 iOS 27 之前的系统上被用于针对特定个人的攻击 | 闭源，且已经有在野使用的公开记录。起步阶段不碰这个文件格式 |
| CoreMedia、Audio | 18.7.11：相机权限、音频信息泄露，都是逻辑问题 | 值得以后用「权限是否被多问了一次」来分类，但你还没有系统的日志可以对照 |
| mDNSResponder | 18.7.9：局域网输入导致的内存问题 | 输入在网络上。起步实验不向网络发探测包 |

18.7.11 的原文：<https://support.apple.com/en-us/149225>。CoreGraphics 那一条用来说明文件解析器的严重性，不作为第一个实验对象。

## 最短路径

做完下面这些就可以开始找候选，其余实验用来补观察能力，不挡这一条线。

1. L0。先把系统更新到软件更新页面给出的最新 18.7。停在 18.7.9 上找到的问题，可能已经写在 18.7.10 或 18.7.11 的说明里。那种「找到了又发现是旧的」最伤节奏。
2. L1。确认 Mac 和 Xcode。
3. L2、L6。自己的 App 里，消息桥拒绝 `example.com`、接受 `lab.local`。你要先看见正确的边界，才认得错误的边界。
4. L9。Mac Safari 的「开发」菜单能检查手机上的 example.com。L15 的两个对照页也用这个 Safari 打开。
5. L13 和 L14。先读懂一份你知道原因的 `heap-buffer-overflow`，再看 zlib 的 `no-crash`。以后只有带源码行号的 ASan 报告才进入笔记。手机「分析数据」里一份未符号化的 `.ips` 不够。
6. L16。一次只追一个已公开的修复，先写回归测试的不变量，再看别的调用点有没有同样的检查。
7. L18。用 L6 的三句话去对 Firefox iOS 的 handler。这是同一类 bug 在第三方开源 App 里的位置。

L3、L4、L5、L7、L8、L10、L11、L12 在这条线旁边。它们让你认得沙盒、ATS、钥匙串、URL 方案、entitlement、系统日志和 sysdiagnose。排期上放在 L6 之后、L16 之前即可。L17 只有预检打印「可以做 L17」才做。编不过就回到 L16 的阅读，阅读本身就能产生「候选」笔记。

## 方法 A：沿着公开修复看相邻调用点

这是这台设备上最早能产生笔记的方法。材料是 Apple 已经写进安全说明的 WebKit Bugzilla 编号，加上 WebKit 仓库里能看见的 diff 和 LayoutTests。

一轮只做这些事，命令都在进阶指南 L16：

1. 从 18.7.9 说明里取一个编号。优先顺序：`309004`（AudioWorklet 与 CSP）、`308675`（CSP 未被执行）、`308906`（CSP）、`309698`（信息泄露）。一次一个。
2. `git log --grep=编号` 没有提交，就说明补丁还没公开。换下一个编号。不要在 Bugzilla 的权限页上耗时间。
3. 有提交时，打开同一提交里的测试，用一句话写下它要求的不变量。写不出这句话，就还没看懂，不要往下看调用点。
4. 用 `git grep` 找同一函数的其他调用点。每个调用点只记「有这项检查」或「没有」。
5. 「没有」的那一处标成「候选」。不写触发页，不改 WebKit 源码去试。
6. 候选要变成「可复现的逻辑差异」，只有一条路：在你运行的 Safari 或 `run-safari` 打开的页面上，看到和 L15 相反的结果，也就是页面打出 `UNEXPECTED`，或 CSP 控制台没有拒绝记录而页面文字被脚本改掉。看到了，用 L19 提交。没看到，笔记保持「候选」。

已公开的相邻点会被别人看过。这一轮的产出经常是「候选」而不是提交。连续三个编号都只得到「检查都在」，是正常结果，换 `find Source -iname '*AudioWorklet*'` 那一类相邻文件，而不是换去看内核。

## 方法 B：用固定不变量看网页安全

不变量只有三句。每句都已经有一个会失败或会成功的对照，所以你知道自己在测什么。

1. 父页面不能读另一个源的 `contentDocument`。对照页是 `labs/sop-control.html`，通过文字以 `expected block:` 开头。
2. `script-src 'none'` 时内联脚本不能运行。对照页是 `labs/csp-control.html`，页面保持 `csp held`，控制台有 `Content Security Policy`。
3. 原生消息桥只接受允许的 host。对照是 L6：`lab.local` 接受，`example.com` 被记成 `bridge ignored`。

读 WebKit 或读 App 时，只问代码有没有维护这三句。维护了，记「有」，结束。少了一处，记「候选」。运行时打破了，记「可复现的逻辑差异」。

iOS 18.7.7 的说明里有 Navigation API 的跨源问题和 script message handler 的跨源问题（<https://support.apple.com/en-us/126793>）。读的时候用方法 A 的同一组命令，把关键词换成你在提交信息里看到的函数名。不要从公告的影响描述去编一个页面。

## 方法 C：只 fuzz 你能编出符号的代码

L13 的报告是样张：`heap-buffer-overflow`、`WRITE of size 8`、分配大小和拷贝长度来自输入的不同字段。以后每一份笔记都要能指出同样的三样东西：错误类型、写了或读了多少、哪个字段是输入给的。

L14 把这套用在 zlib 上。`PASS zlib no-crash` 表示这 30 秒没有发现。把时间拉长之前，先满足两个条件：库是你用 `-fsanitize=address,fuzzer-no-link` 编的，崩溃栈里有源码文件名。系统自带的、没有符号的库不作为目标。

WebKit 编过（L17 的 `BUILD_EXIT:0`）之后，下一步才是它树里的解码器。先定位，不要猜路径：

```bash
cd ~/ios-research/WebKit
find . -type d \( -name libpng -o -name libwebp -o -name zlib \) | head
```

`find` 为空就停。不要为了找目录改克隆方式。有目录时，沿用 L14 的编法：静态库加上 `fuzzer-no-link` 和 AddressSanitizer，驱动文件只调用一个解码入口。30 秒没有 `ERROR: AddressSanitizer` 就记 `no-crash`。有报告就按 L14 的「只有崩溃」停下来读，不写利用。

手机上的确认放在最后，而且只确认你已经在 Mac 上复现的那一个输入：用 L15 的本地服务器打开该文件，看「分析数据」里是否新出现 WebContent 或 Safari 的 `.ips`。没有 Mac 上的符号栈时，不要从手机日志开始。

ImageIO 和 CoreGraphics 仍停放。它们在公告里级别高，也正因为闭源，不能作为第一轮正反馈。

## 方法 D：开源 App 里的同一处消息桥

L18 的三问是完整的一轮。对象是 Firefox iOS，因为仓库公开，而且 `WKScriptMessageHandler` 还在维护。

一轮的产出是三句答案。`didReceive` 没有读 `frameInfo.request.url` 时，记「候选」，并写明检查如果存在，应该在被调用的那一层。不要对安装在手机上的 Firefox 或账号页面做实验。报告渠道用该仓库的 `SECURITY.md`，没有就保持候选。

做完 Firefox 这一轮之前，不要换第二个 App。换目标会把时间花在找仓库上。

## 一轮结束时怎么记

打开 `labs/bug-note.md`。结论只留四个里的一个。

| 结论 | 你手上有什么 | 下一步 |
| --- | --- | --- |
| 练习崩溃 | L13 的样张 | 去做 L16 |
| 候选 | 指出了缺少的检查，运行时还没看到错误行为 | 换下一个 Bugzilla 编号，或把 L18 的三问写完。不提交 |
| 可复现的逻辑差异 | 运行中的页面或 App 出现了和对照相反的结果 | L19 |
| 只有崩溃 | ASan 报告，还说不清输入的哪个字段决定了写到哪里 | 停在这份报告上，把三样东西补进笔记。补不出就保持这一类，不提交 |

正反馈指的是表格里后三类里，你独立写完的第一张笔记。L13 的练习崩溃用来校准格式，不计入。

连续几张都是「候选」或「检查都在」，说明方法 A 在正常工作。这时继续下一个 WebKit 编号。不要把「还没提交」理解成该去看内核或越狱。

## 和公告同步的习惯

每装一次软件更新，只做这一件事：打开 <https://support.apple.com/en-us/100100>，点进刚刚安装的那个 iOS 18.7 版本，把组件名抄下来，分成两列。

- 左列：WebKit、zlib，以及任何你能在 `~/ios-research` 里打开源码的名字。这些进入方法 A 或方法 C 的队列，一次一个。
- 右列：Kernel、Wi-Fi、ImageIO、CoreGraphics、Sandbox、App Intents。这些留在右列，直到你已经有一张「可复现的逻辑差异」或一张写全了三个字段的「只有崩溃」。

18.7.11 的 CoreGraphics 已经在右列。它说明图形解析器仍会被使用，也说明这类问题的验证材料不在公开源码里。你的入口仍然是方法 C 里编得过的解码器。
